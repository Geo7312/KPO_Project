# Управление исходным кодом RepairDesk

## Коммиты и ветки

Сообщение коммита оформляется как `тип(область): краткое действие`, например `test(orders): cover client refusal`. Допустимые типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, `build`. Локальный хук `.githooks/commit-msg` включается командой `git config core.hooksPath .githooks`; CI дополнительно проверяет сообщения новых коммитов в push и pull request. Первый коммит `chore: initial RepairDesk project` уже соответствует правилу.

Стратегия GitHub Flow:

1. От актуального `main` создаётся короткоживущая ветка `feature/...` или `fix/...`.
2. Изменения сохраняются атомарными коммитами с проверяемым сообщением.
3. Ветка отправляется на GitHub, открывается pull request в `main`.
4. После успешного `RepairDesk CI / verify` и проверки изменений pull request сливается в `main`.
5. Ветка удаляется после слияния. Непосредственный push в `main` не используется.

Для проверки слияния локально без изменения `main` можно выполнить `git merge --no-commit --no-ff feature/lab5-ci-metrics`, просмотреть результат и отменить подготовленное слияние `git merge --abort`. Реальное слияние должно проходить через pull request.

## Защита основной ветки

В GitHub откройте **Settings → Rules → Rulesets → New ruleset → New branch ruleset**. Назовите правило `Protect main`, выберите ветку `main`, включите **Require a pull request before merging**, **Require status checks to pass** с проверкой `verify` из workflow `RepairDesk CI`, а также **Block force pushes** и **Restrict deletions**. После первого запуска CI добавьте `verify` в обязательные проверки. Если интерфейс предлагает обход правил для владельца, отключите обход для регулярной работы. Эти параметры действуют только после сохранения правила в GitHub; наличие этого файла само по себе ветку не защищает.

## Автоматические проверки

Workflow `.github/workflows/ci.yml` запускается при push в `main` и `feature/**`, при pull request в `main`, а также при теге `v*`. Он проверяет сообщения коммитов, форматирование C#, собирает проект, запускает модульные тесты с покрытием и интеграционную smoke-проверку. При успехе формируется архив Windows-приложения. На теге после успешной проверки создаётся GitHub Release с архивом.

Развёртывание в тестовую среду не включено: это необязательный пункт задания, а RepairDesk — WPF-приложение для Windows, не веб-сайт. В качестве проверяемого результата сборки используется архив приложения.

## Метрики

Скрипт `.github/scripts/measure.ps1` создаёт `artifacts/metrics.json` для каждого запуска CI. Этап берётся из ветки: `implementation` для обычной разработки и `release` для тега. Отчёты сохраняются как артефакты запусков; значения не подменяются вручную.

| Метрика | Источник |
| --- | --- |
| Пройденные тесты | TRX, поле `passed` |
| Упавшие тесты | TRX, поле `failed` |
| Общее число тестов | TRX, поле `total` |
| Время выполнения тестов | Сумма `duration` в TRX |
| Покрытие строк | Cobertura `line-rate` |
| Покрытие ветвлений | Cobertura `branch-rate` |
| Предупреждения сборки | `build.log`, диагностики CS/CA/IDE |
| Число коммитов | `git rev-list --count HEAD` |

Результаты разных этапов сравниваются по артефактам соответствующих запусков Actions. Первый локальный замер не считается доказательством работы удалённого CI.

## Релиз

После слияния и проверки `main` создайте аннотированный тег и отправьте его: `git tag -a v1.0.0 -m "Release 1.0.0"`, затем `git push origin v1.0.0`. Workflow проверит код и опубликует архив в GitHub Releases. Тег нельзя создавать до успешного слияния и проверки основной ветки.
